##  Краткое содержание подготовленных материалов

### 1. Паспорт модуля (README.md)
* **Назначение:** Обеспечение консольного интерфейса для запуска симуляции с кастомными параметрами напрямую из терминала.
* **Границы:** Модуль отвечает исключительно за парсинг флагов, их валидацию и диспетчеризацию вызовов в ядро симулятора. Расчетами, логикой планировщика и ведением логов симуляции CLI не занимается.
* **Контракт:** Зафиксированы 4 планируемых флага: `--duration / -d`, `--ue-count / -n`, `--scheduler / -s` (строгий выбор между *RoundRobin* и *ProportionalFair*) и переключатель `--qos`.

### 2. Структура и потоки данных (docs/diagrams.md)
* **Текущее состояние (AS-IS):** Помечено как `не применимо`, поскольку код модуля еще не создавался.
* **Целевая архитектура (TO-BE):** Спроектированы две текстовые диаграммы в формате **Mermaid**:
  1. Схема обработки и валидации аргументов командной строки через пакет `argparse`.
  2. Диаграмма последовательности вызовов (`sequenceDiagram`) между пользователем, скриптом `sim_cli.py` и функциями ядра бэкенда.

### 3. Ревизия с доказательствами (docs/audit.md)
Поскольку код CLI отсутствует, аудит проведен в отношении файлов бэкенда, с которыми интерфейсу предстоит интеграция.
* Зарегистрированы наблюдения **AUD-001** и **AUD-002** по файлу `TEST_MODULES.py`.
* Зафиксирован технический долг: параметры длительности симуляции, планировщиков и количества пользователей жестко захардкожены внутри функций `sim_with_manager` и `sim_with_manager_qos`. Без изменения их сигнатуры интеграция CLI невозможна.

### 4. План развития и зависимости (docs/features.md)
* Оформлено предложение **FEAT-001** на создание базового интерфейса команды `run`.
* Сформулированы критерии приемки: успешная отработка команды запуска с кастомными параметрами без падения ядра.
* Зафиксированы риски: потенциальный сбой графического вывода `matplotlib` (из ядра) при работе в консольной среде WSL без X-сервера.
